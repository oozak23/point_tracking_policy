Building the Action Decoder

How the decoder block was built and verified, which loss it trains on and why, when robot proprioception was added and what it changed, and every training run and test behind the current numbers.

Frozen Track-On-R turns object points into the scene memory. A trainable replica of Track-On's own decoder layer carries the robot points, reads its own history, and cross-attends into that scene memory. One readout query per frame becomes one action.

The block

Two streams, one trained. Everything below the dashed box is new code; Track-On stays frozen and is never back-propagated through.

Why a replica and not Track-On itself. Track-On's own layer opens with attention over the whole frame feature map, because it does not know where its point is and has to search. We do know — forward kinematics gives the exact pixel — so the replica drops that stage. That is what makes the cached token stream sufficient and 5.3 PB of feature maps unnecessary. The attention block itself is imported from Track-On rather than re-implemented, so heads, MLP ratio and norm placement are identical by construction.

Settled configuration. D=256, 3 layers, memory M=24 and scene slots 24 (Track-On's own recipe), window T_win=48, batch 16, one-step prediction (k=1) at 7.2 Hz — the policy predicts the action 0.14 s ahead. Runs are pinned to an L40S; the shared queue otherwise mixes in T4s that are ~10× slower.

How it was built

Seven steps, each one verified before the next was started. Verification is by perturbation: change an input that must not matter and require the output to be bit-identical, change one that must matter and require it to move. Reading code and agreeing with it is not evidence — two real defects below were invisible to reading.

  1. 1

    Dataloader

    Samples a 48-frame window: scene tokens (48+23, 100, 256), robot tokens (48+23, 128, 256), validity masks, the 10-dimensional action target per frame, and the clip's tracking-quality weight.

    Verified: 5 checks — causal slicing, padding, mask conventions, episode-level train/val split, throughput.

  2. 2

    Replica block

    Point attention → per-point memory attention → scene cross-attention.

    Verified: 9 perturbation checks. Two findings. The memory was dead: "changing the past must move a later frame" failed with delta exactly 0 — the FIFO started empty at the first supervised frame, so the robot's own history was never read. Fixed by rolling the FIFO over the whole stream as warm-up. The memory attention did 25× redundant work — it pushed all 25 slots through the block but only ever reads the last one; everything after the attention is position-wise. Computing one query is bit-identical and far cheaper.

  3. 3

    Readout

    k learned queries cross-attend over the robot points with padding masked; k=1 in every run so far.

    Verified: 8 checks, including NaNs planted in padded slots. Found NaN gradients in the time embedding when every scene key was masked during front-padding; the memory now runs only on live rows.

  4. 4

    Head

    Three linear projections: body-frame translation in metres, raw 6D rotation, gripper logit. Initialised near zero motion and identity rotation, so the policy starts at "stay still" rather than at noise.

    Verified: 10 checks — a known +90° rotation to catch a transposed convention, 128 random rotations round-tripping at 1e−12, proper rotations from degenerate inputs, finite-difference gradients.

  5. 5

    Loss

    Weighted behaviour cloning, with the group scales measured on training data only. Section below.

    Verified: 10 checks, including that touching a validation label makes the scale job fail.

  6. 6

    Training loop and the overfit gate

    Before any real run: can the model memorise 10 hand-picked windows (480 targets, 14 gripper changes)? It passed at update 150 and stopped automatically — loss 2.267 → 0.019, position 11.3 → 1.03 mm, rotation 1.67° → 0.20°, all 14 gripper transitions correct. So the wiring carries gradient end to end.

    Verified: 6 checks, plus a CPU smoke run that exposed the learning-rate problem below.

  7. 7

    Held-out evaluator, with the gates fixed in advance

    Frozen validation windows, the copy-last baseline, gripper-event matching with penalties for missed and extra events, per-lab breakdowns, and the memory interventions. The pass marks were written to validation_plan_v1.json before the first run was submitted, so no threshold could be moved afterwards.

    Verified: 4 checks plus offline end-effector integration against saved FK (maximum disagreement 0.00002 px).

The loss, and why this one

The policy imitates the demonstrator: at every frame it predicts the next action the operator took. One term per group, each divided by that group's own scale, all three coefficients 1.

position = ‖Δp̂ − Δp‖² / s_p² s_p = 0.016682 m (RMS displacement) rotation = ½‖R̂ − R‖_F² / s_r² s_r = 0.045676 (≈ 2.617°) gripper = BCEWithLogits(logit, open_next) loss = Σ(weight · valid · per-frame) / Σ(weight · valid)

Why scale the two continuous groups at all?

Metres and rotation matrices are different units; without scaling the mix of the three terms is arbitrary. The scales are the RMS of the labels themselves, measured over the training split only (12,123 clips, 9,441 episodes, 1,924,243 valid frames). This puts the do-nothing baseline — zero translation, identity rotation — at a loss of exactly 1 per component, so the number says immediately whether the model beats standing still.

Why squared error and not Huber?

Huber protects against outliers in the labels. These labels are exact: recorded end-effector poses, not estimates. There is nothing to protect against, and at δ=1 Huber would put 43% of frames into its linear region — exactly the small, precise motions that the model is worst at, down-weighted.

Why one scale per group and not per dimension?

Standardising each of the six rotation coordinates separately would divide by their individual standard deviations. Two of the six barely vary in this data, so they would be multiplied by ~731× — the loss would be dominated by the rotation the robot never performs.

Why the clip weight?

Tracking quality varies. Rather than deleting the noisier clips, each clip carries a weight from its measured tracking error, so a poorly tracked video counts for less but still contributes. Frames with invalid labels are removed before any arithmetic, so they cannot leak in as NaNs.

One thing the loss alone did not fix.

With a single learning rate, the first update pushed position error from 0.84 cm to 9.6 cm. Adam normalises by gradient statistics and so ignores the physical units of each output. Multiplying the position and rotation projection rates by their own loss scales fixed it; the rest of the network keeps the base rate.

Proprioception: when, and why

When. 11 September, immediately after the first one-epoch pilot failed all three gates.

Why. The failure was specific, not general. Position error was 9.99 mm against a 4.55 mm copy-last baseline, but the gripper behaviour was the striking part: 1,889 spurious open/close events and a timing cost of 5.77 frames. The policy could see the robot only through tracked pixels — it had no access to its own joint state, and nothing at all tells it how wide the gripper currently is when the fingers are occluded. Adding the robot's own sensors is the cheapest possible test of "is an input missing?", and it is what a real controller would have anyway.

What was added. Joint positions q (7), joint velocities q̇ (7) and current gripper width (1), each on a fixed scale, through a small encoder added to the action token just before the head — late fusion, 69,888 parameters, final projection zero-initialised so the model starts identical to the visual one.

The leak test. The obvious danger is handing the model the answer. A dedicated check confirms only frame t's state is read, never t+1, and that no target field reaches the encoder — plus five more checks on alignment, padding, identical initialisation and checkpoint restoration. All 6 passed, along with the 6 existing training checks and an end-to-end smoke run.

What it changed. At equal budget it cut position error by 2.3 mm and all but removed the spurious gripper events — 1,889 down to 136 — bringing the transition-timing gate from failing to passing. It also halved the scene-shuffle effect, which is the uncomfortable part: see the tests below.

The tests

Low error on its own would not tell us the model is using the scene memory — the point of the whole design. So each finished run is also probed by intervention: replace one input with another episode's, keep everything else fixed, and measure how much worse the predictions get. A memory that matters is expensive to corrupt.

Donor episodes are fixed in the frozen plan, so the shuffle is reproducible rather than random. Scene and proprioception rows are measured on all 63,598 targets; the robot-history row uses the smaller paired subset the protocol reserves for it (~1,300 windows), against its own clean baseline. The pattern is consistent across every run: the policy leans hard on its own motion history and barely on the scene.

Splitting the scene test by difficulty

A 2–9% effect could be an average hiding something real: most frames are mid-motion, where "keep going" is right and no scene could help. If the model used the scene exactly where the motion changes, the effect would be concentrated there. So frames were binned into five equal groups by how badly copying the previous action does on them, and the same shuffle re-run per bin, with confidence intervals from a bootstrap over whole windows.

Each run reproduced its own overall number exactly before being split — and then the effect came out flat. For the five-epoch visual model: +9.1% on the easiest frames, +8.4% on the hardest, and +7.5% within ±2 frames of a gripper change — if anything lower where the scene should matter most. The proprioception run is equally flat at about 2%. Longer training raises scene use everywhere without teaching the model when the scene matters.

One caveat worth stating: points on a grasped object move with the gripper, so shuffling the scene also removes a second copy of the robot's own motion. Part of that 8.7% may be motion information, not object locations. Splitting on whether the gripper is closed would separate the two.

What the numbers say

Two separate problems, and they need different fixes.

1 · The motion is imprecise. At 6.49 mm the policy is still 1.4× worse than simply repeating the previous action. Predicting one step ahead at 7.2 Hz is dominated by momentum, so a model that regresses the absolute action spends its capacity re-deriving a quantity it is already given. Predicting the residual — how the action differs from the last one — targets exactly the part that is not momentum.

2 · The scene is under-used, uniformly. Neither more training nor better inputs moved scene use where it should matter. One-step prediction simply does not require it: you can be right for 0.14 s without knowing where anything is. Predicting a chunk of ~16 future actions at once (as ACT does) makes the objective require the scene, because you cannot extrapolate two seconds of motion from momentum alone.

Training is not the bottleneck: train and validation errors stay within 0.2 mm of each other in every run, so the model is underfitting, not memorising. There are 32,031 further unused episodes available, but more data does not help a model that is not yet fitting what it has.

  1. A

    Residual target, action chunking, or both?

    Residual targets are a one-line change to the labels and directly attack problem 1. Chunking is a larger change — new targets, a k>1 readout — and attacks problem 2. They are compatible.

  2. B

    If we chunk, does the loss shape change?

    Averaging over a chunk with a squared error re-introduces averaging over possible futures. A per-step weighting, or a distributional head, is the alternative.

  3. C

    Should the gripper target be the observed state or the operator's command?

    Today it is the next observed width. DROID also records the command itself, which leads the observed state by a few frames. The command is what a controller would actually output.
